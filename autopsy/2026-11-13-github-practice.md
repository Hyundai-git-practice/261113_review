# 부검: GitHub 학습 내용을 실제 저장소 운영으로 연결하기

> 이번 부검은 특강에서 다룬 주제를 바탕으로, 학습 내용을 실제 저장소에 적용할 때 발생할 수 있는 취약 지점과 예방 방법을 점검한 기록이다. 실제로 발생했다고 확인되지 않은 오류를 장애 사례로 단정하지 않는다.

## S — Situation (상황)

GitHub 프로필 README, Markdown, Git 명령어, 저장소 관리 방법을 학습했다. 개념을 알고 있는 것과 실제 저장소에서 실수 없이 적용하는 것은 다를 수 있다. 특히 파일 변경, 커밋, 브랜치 전환, 원격 저장소 반영 과정에서는 확인 절차가 중요하다.

## T — Task (점검 과제)

학습 내용을 실제 작업에 적용할 때 놓치기 쉬운 부분을 찾아보고, 문서 품질과 변경 이력의 신뢰성을 높일 수 있는 예방 절차를 정리한다.

## A — Action (원인 및 대응 분석)

### 점검 항목 1. README가 읽기 어려워지는 문제

- **가능한 원인:** 제목 계층이 불규칙하거나 긴 문단이 이어지고, 배지와 이미지가 과도하게 사용됨.
- **영향:** 방문자가 핵심 역량과 프로젝트 정보를 빠르게 찾기 어려움.
- **예방:** 제목 구조를 통일하고, 핵심 정보를 위쪽에 배치하며, 표와 목록을 필요한 곳에만 사용한다.

### 점검 항목 2. Markdown 렌더링 오류

- **가능한 원인:** 코드 블록의 백틱 개수 누락, 링크 주소 오류, 목록 들여쓰기 불일치.
- **영향:** 문서 레이아웃이 깨지거나 코드와 일반 문장이 구분되지 않음.
- **예방:** 수정 후 GitHub 미리보기 화면에서 제목, 목록, 링크, 코드 블록을 확인한다.

### 점검 항목 3. 잘못된 파일을 커밋하는 문제

- **가능한 원인:** `git status`를 확인하지 않고 `git add .`를 실행함.
- **영향:** 임시 파일이나 불필요한 변경 사항이 커밋에 포함될 수 있음.
- **예방:** 커밋 전 `git status`와 `git diff --staged`를 확인하고, 필요한 파일만 스테이징한다.

### 점검 항목 4. 원격 저장소와 로컬 저장소의 차이

- **가능한 원인:** 원격 변경 사항을 확인하지 않고 작업하거나, 다른 브랜치에 push함.
- **영향:** 충돌이 발생하거나 의도하지 않은 브랜치에 변경 사항이 반영될 수 있음.
- **예방:** 작업 전 브랜치와 상태를 확인하고, 필요하면 `git pull`로 원격 변경 사항을 반영한 뒤 push한다.

## R — Result (결과 및 재발 방지)

이번 점검을 통해 GitHub 작업에서 중요한 것은 명령어 자체보다 각 단계의 확인 습관이라는 점을 정리했다.

앞으로 다음 순서를 기본 체크리스트로 사용한다.

1. 작업 전 `git status`와 현재 브랜치를 확인한다.
2. 수정한 파일의 내용을 다시 읽고 Markdown 렌더링을 확인한다.
3. `git diff`로 변경 내용을 검토한다.
4. 필요한 파일만 `git add`로 스테이징한다.
5. `git diff --staged`로 커밋 대상 내용을 확인한다.
6. 변경 목적이 드러나는 메시지로 커밋한다.
7. 원격 저장소와 브랜치를 확인한 뒤 push한다.

**핵심 교훈:** 실수를 완전히 없애려 하기보다, 실수가 원격 저장소에 반영되기 전에 발견할 수 있는 확인 절차를 습관화하는 것이 중요하다.
